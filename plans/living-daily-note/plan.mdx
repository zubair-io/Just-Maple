# Outcome

Just Maple opens to an editable note for today. A user writes a paragraph, adds a task, sees an incoming source block, clears the source with Undo, and moves the same task to tomorrow. An empty day means there are no visible blocks needing attention; history and notebook files remain available. The desktop and iPhone share the daily-note UI and truthful persistence/sync state.

# Durable model and decisions

`DailyBlock` has a stable ID, local calendar day, kind (text, heading, task, email, message, code), content, order, version, creation/update timestamps, actor, user-edit flag, optional clear/completion timestamps, source provenance, and optional canonical task ID/version. `DailyNoteSnapshot` contains day, named time zone, active and cleared blocks, and diagnostic revision. The source event remains immutable evidence; block text is editable. Once a user edits content, automatic source refresh updates provenance without replacing their words.

Add `daily_notes` and `daily_blocks` with an additive migration called from `KnowledgeStore.init`. Reuse `WorldStore.command` for atomic idempotent commands and `world_history` for before/after snapshots. Source keys deduplicate repeated imports, including cleared tombstones. A move updates placement of the same block, never creates a copy. Clear hides a block without completing a linked task or sending anything. Explicit task completion clears the daily block and, when linked, updates its canonical task atomically. A daily-created task is a standalone block; completing it does not invent a canonical LifeTask. Restoring a completed block does not silently reopen the canonical task.

All user mutations require a request ID and expected block version. A reused ID with a different payload fails. Conflicts preserve the draft and expose a retry/reload choice. Actor identity comes from the trusted host, not arbitrary browser input. Dates use validated `YYYY-MM-DD` plus an IANA time zone and calendar arithmetic; reads of future days do not trigger rollover. Carry-forward occurs when entering the actual current day, moves only unfinished task blocks from older days, and retains block identity. Cleared/completed items and ordinary writing remain in history.

Incoming projection selects accepted open canonical tasks and actionable notify/ask-user source events already persisted through `KnowledgeStore.ingest`. It does not dump all imported mail into Today. Source updates use stable identity and do not resurrect cleared blocks. No email sending, external deletion, new backend, or invented live model answers are added.

# Native and mobile contract

Mac bridge commands: `dailyNote {day,timeZone}`, `dailyBlockMutate {record}`, `dailyBlockHistory {id}`, and `dailyCarryForward {day,timeZone,requestID}`. `DailyBlockMutation` carries kind, blockID, expectedVersion, requestID, day, timeZone, optional content/blockKind/targetDay/position. Mutation kinds are create, edit, clear, restore, move, complete.

The iPhone uses its existing encrypted durable outbox and Mac acknowledgments. Daily snapshots include optional `sync {status, pending, conflicts, asOf, partial?}` metadata. Cached and pending states remain visible; queuing a command does not claim the Mac accepted it. A day absent from the device cache reports unavailable rather than an empty day. Initial phone cache covers the Mac's recent/current/next-day projections; arbitrary historical reads remain Mac-owned until synchronized. Payload bounds preserve whole editable blocks and report partial snapshots. Missing block history on the phone reports unavailable. An empty cached day never claims that all underlying obligations are resolved. Existing pairing and offline controls remain available.

# Delivery boundaries

This build proves the daily-note product loop with durable local storage and existing connector/companion infrastructure. Sending a block as an email or message, external provider edits, a new graph engine, and broad migration of legacy notes are future work; blocks retain provenance and stable IDs so these can be added safely. The current implementation does not promise an autonomous model editor for arbitrary prose: trusted source/task updates maintain bot-owned fields while user edits remain protected.

Manual block reordering is deferred from this first cut; insertion order is stable. No unresolved product choices block implementation. Checkpoint status, test evidence, and any contract changes will be recorded here as work proceeds.
